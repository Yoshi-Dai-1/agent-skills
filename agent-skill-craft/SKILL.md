# Agent Skill Craft

Agent Skill（`SKILL.md` を含むディレクトリ）の設計・執筆・監査・改修・評価に関する実行プロセスを定義する。

## 概要と前提

- **ドメイン非依存**: 事務手続き、文書作成、思考プロセス、データ処理、開発等、あらゆる領域のスキルに同一のプロセスを適用する。特定領域の固有の規則を本プロトコルへ持ち込まない。
- **指示文と成果物の文体を分離する**: `SKILL.md` に書く指示文は AI エージェントが読む。対象スキルが生成する成果物の文体は、対象ドメインと読み手の決定に従う。文書作成・翻訳・報告のスキルでは成果物に散文が含まれるのが正しい。
- **既存コンテキストの尊重**: 既に存在するコード、設定、正本データ、既存文書の構造を最優先で参照・継承し、重複や競合を発生させない。
- **各フェーズは到達すべき状態を定める。手順の一意な泳ぎ方を定めるものではない。** 同じ結果へ到達する別の手順があるときは、利用者と合意できる範囲で最も適切なものを選ぶ。順序や手順が固定されている箇所だけが厳密に指定する。

## 適用範囲

- 本スキルの範囲: Agent Skill の設計・執筆・監査・改修・評価、および評価設定の立案。
- 範囲外: 対象スキルの業務領域そのものの実装。対象スキルの実行時に行う具体的な業務処理については、Phase 4 が参照する実行時規律を適用する。
- **範囲外の入力を疑ったら、処理せずに理由を述べて利用者に確認する。** 範囲外の入力を対象内として処理しない。

## 段階的実行フェーズ（Phase Protocol）

各フェーズに参照ファイルと読み込み条件を示す。条件に該当しないファイルは読み込まない。

### Phase 0: 対象の確定（Scope & Intent）

1. **対象の特定**: 作成／監査／改修の別、対象スキルの名称とディレクトリ、想定される利用タスクを確定すること。
2. **既存物の読み込み**: 対象ディレクトリが存在する場合は `SKILL.md`、`references/`、`scripts/`、`assets/`、`evals/` を全件読み込み、既存の設計を継承する。**`references/` が無い場合は Phase 1 と Phase 2 で新規に作成し、`evals/` が無い場合は Phase 3 の Layer C で新規に作成する。いずれも作成または改修の依頼に限る。監査のみの依頼では作成しない。**
3. **条件の確定**: 対象スキルのドメイン、出力物の読み手（機械可読か人間向けか）、実行環境（必要なツール・依存）を確定すること。
4. **評価方式の確定**: 対象スキルの出力が客観的に検証可能かを判断し、`references/evaluation.md` §3.1 の方式（A 機械的 assertion／B 人手レビュー／C 両者）から 1 つを選んで記録する。判断できない場合は利用者へ 1 行で確認する。**この判定に必要な `references/evaluation.md` §3.1 のみを読み込む。**

### Phase 1: 公式仕様への適合設計（Specification Conformance）

1. `references/specification.md` を読み込み適用する。**このフェーズでは常に読み込む。**
2. 規定的要件（フロントマター、`name` と `description` の規則、ディレクトリ構成、ファイル参照規則、段階的開示の予算）を満たす設計を確定する。
3. 裁量的要件（参照ファイルの分割粒度、スクリプトの要否、アセットの要否）は、対象スキルの規模と利用頻度を勘案して判断し、判断根拠を記録する。**本スキルは分割の型を固定しない。**

### Phase 2: 執筆（Authoring）

1. `references/authoring.md` を読み込み適用する。**`SKILL.md` 本文または参照ファイルを執筆・改稿する段階では常に読み込む。**
2. 対象スキルの落とし穴として実際に観測した事象を `SKILL.md` の Gotchas として蓄積する。
3. 出力形式が定まる場合は、テンプレートを `assets/` に置く。対象スキルの新規作成では、`assets/skill-template.md`、`assets/reference-template.md`、`assets/evals-template.json`、`assets/trigger-queries-template.json` を土台に複製する。**複製したファイルは対象スキルの `SKILL.md` から参照する。** 本スキルの `assets/` は 対象スキルの作成と改修の手直しにのみ使い、対象スキルの実行時には読み込まない。
4. **作業モードが監査のみの場合は、このフェーズでファイルを変更しない。** 違反箇所と修正案を報告するにとどめる。

### Phase 3: 検証（Verification）

1. **Layer A（機械検証）**: `python3 scripts/validate-skill.py <対象スキルディレクトリ>` を実行する。公式の検証ライブラリが利用できる場合は `skills-ref validate <対象スキルディレクトリ>` も実行する。**公式の検証ライブラリが利用できない場合は `skills-ref` による検証だけを省略し、省略の事実と理由を報告する。Python 3 の実行環境がない場合はこの Layer 全体を省略し、Layer B の機械走査を grep による全文検索に置き換える。** いずれの省略も Layer B の報告に記す。
2. **Layer B（証拠付き自己監査）**: `references/audit-protocol.md` を読み込み適用する。**`scripts/audit-ledger.py` で未決済台帳を管理し、引用と行番号を伴わない指摘は採用しない。** Layer A の検出結果も台帳に登録する。対象を全件走査し、未決済ゼロをもって終了する。
3. **Layer C（評価）**: `references/evaluation.md` を読み込み適用する。**トリガー評価は全件で必須**（`evals/trigger-queries.json`）、**出力評価は Phase 0 で決定した方式で必須**（`evals/evals.json`）。対象スキルに `evals/` が無い場合は、作成または改修の依頼であればこの Layer で新規に作成し、監査のみの依頼であれば作成せずに評価の不実施を報告する。

### Phase 4: 実行時規律の埋め込み（Runtime Protocol Embedding）

1. `references/execution-protocol.md` を読み込み、対象スキルの `SKILL.md` へ実行時規律（計画の構造化と検証、対象全件の列挙と完了条件、範囲変更の事前合意、完了報告の 4 区分、手段の抽象化とフォールバック、同じ対象には同じ語、適用範囲外の実行）を反映する。**このフェーズは対象スキルの実行時命令を設計または改修する場合にのみ行う。**
2. **対象スキルが既に同等の実行時規律を持つ場合は、重複して書き足さない。** 既存の記述を参照で代替する。
3. 反映後、Layer A と Layer B を再実行して、反映漏れがないことを確認する。ただし再走査の対象は、**今回の反映で決済した項目と、それによって新たに発生しうる影響範囲に限る。** 全件を読み直す再監査は行わない。
4. 反映が対象スキルの `description` に及んだ場合は、トリガー評価も再実施する。

## 利用可能なスクリプト

- **`scripts/validate-skill.py`** — 公式仕様と運用ルールへの適合を検証する。終了コード `0`=適合、`1`=不適合、`2`=使用法エラー。
- **`scripts/audit-ledger.py`** — 監査の未決済台帳を管理する。終了コード `0`=成功、`1`=台帳エラー、`2`=使用法エラー。

## 語彙と表記の基準

- `references/vocabulary.md` を読み込み適用する。**語彙を使う記述では常に読み込む。**
- 語彙揺れは `assets/vocabulary.json` に保持し、`python3 scripts/validate-skill.py <対象スキルディレクトリ> --vocabulary assets/vocabulary.json` で機械検証する。
- 異物混入（他言語の語、文字化け、日本語文中の正体の不明な英単語）は `assets/foreign-tokens.json` を基準に検出する。

## Gotchas

実地運用で実際に踏んだ落とし穴のみを記す。一般論や自明な事実は記さない。

- **自己監査の反復**: 最終確認を反復すると、決済済みの指摘を新規として再掲し、監査が成立しなくなる。未決済台帳を持ち、決済済みは再掲しない。引用なしの指摘は採用しない。引用は監査時点の現行ファイルから取得し、記憶の文面で代替しない。
- **実行範囲の過剰表示**: 対象全体と宣言しながら一部のみを実施し、報告でも全体と書いた。宣言した対象と実施した対象を一致させ、完了条件には件数を明記する。
- **手段の固定**: 特定の手法を名指しすると、実行環境の変化で実行できなくなる。能力記述にしてフォールバックを定義する。
- **適用範囲の勝手なる狭め**: 適用範囲を明示しないまま一般的知識から対象を推定すると、意図しない範囲で対象を限定し、対象外の入力を誤って対象外として扱う。適用範囲を冒頭に宣言する。
- **description の undertrigger**: description が「何をするか」だけの説明型になると発動しない。命令形に書き、利用者が領域名を明示しない場合の発動条件も列挙する。
- **成果物文体の誤適用**: 指示文向けの文体規則（読み手向けの解説を排する等）を、対象スキルの成果物にも適用すると、文書作成系スキルの散文まで潰す。対象と成果物の文体を分ける。
- **他言語の混入**: 日本語の文中に他言語の語が混入すると、文として成立しなくなる。文字化けを検出するだけでは足りないため、スクリプト単位で検出する。
- **自己点検の不備**: 自分が作った検証器は、自分のファイルも検証する。検出器が使う語彙データは検証対象から除外し、検出器自身に混入があると誤検知する。

## よくある誤り

- 対象スキルの **指示文の文体**と**成果物の文体**を同一の規則で扱う。
- 機械で判定できる項目（存在・構文・リンク・命名規則・異物混入・語彙揺れ・サイズ予算）を人手だけで判定する、またはその逆。
- 対象スキルが **生成しない**成果物の形式を、対象スキル自身に要求する。
- 評価を省略した状態で「品質が向上した」と報告する。
