# 評価規律（Evaluation Protocol）

対象スキルの品質を測るための規律。**必ず評価する対象を規定し、評価の形式は対象スキルの客観性に応じて選択させる。**

## 1. 必ず実施する 2 つの評価

| 評価 | 対象 | 形式 | 必須性 |
|---|---|---|---|
| **トリガー評価** | `description` | 実利用者相当のクエリ集合に対し発動率を測定 | **全スキルで無条件必須。** 形式に選択肢がない（`description` は文字列であるため） |
| **出力評価** | スキル全体の挙動 | 対象スキルの客観性に応じて 3 方式から選択 | **全スキルで必須。** 方式の選択のみが対象依存 |

- トリガー評価を省略すると、スキルの存在意義がゼロで終わる。**発動しないスキルは書いたものと等しい。**
- 出力評価を省略すると、品質改善の可否を判定できず、修正が主観の議論に終始する。

## 2. トリガー評価

### 2.1 クエリ集合の作り方

- 20 件を用意する。`should_trigger` 10 件、`should_not_trigger` 10 件。
- **should_trigger**: 表現の揺らぎ（改めた文面・くだけた文面・略語・誤字を含む）、明示性の違い（領域名を直接言う／要求内容から推させる）、詳細量の振れ（短文／長文）、複雑さ（単一手順／多段階）を振らせる。**利用者が領域名を明示しないが確かにスキルが要るケース**を必ず含める。
- **should_not_trigger**: キーワードは共有するが実際に必要なのは別物という **near-miss** を中心にする。明らかに無関係な項目は価値が無い。隣接領域・曖昧な表現・別ツールが適する文脈を含める。
- 実利用者の文面を模写する。ファイルパス、利用場面、固有名詞、列名、略語、誤字を含める。

### 2.2 測定と判定

- 各クエリを 3 回実行し、発動率（発動した回数 / 実行回数）を算出する。
- 合格判定: `should_trigger` は発動率 0.5 超、`should_not_trigger` は発動率 0.5 未満。
- **過学習を避けるため、`should_trigger` 群と `should_not_trigger` 群のそれぞれを、学習用 60% と検証用 40% に固定分割する。** 群ごとに分割することで、各群の合格判定を維持する。分割はクエリ作成時に固定し、以後は変更しない。学習用の失敗のみを修正の手がかりとし、検証用は改善が一般化したかのみ確認に使う。
- 検証用の成績が最良の版を採用する（学習用の成績が最良の版ではなく）。
- description の修正は通常 5 回で足りる。回数は多くなければよい。

### 2.3 手順

1. クエリ集合を作成する → 利用者へ提示して承認を得る（誤ったクエリは誤った description を生む）。
2. 現在の description を学習用・検証用の両方で評価する。
3. 学習用の失敗のみを根拠に description を修正する。失敗クエリの固有キーワードを直接追加しない（過学習）。失敗が表す一般的なカテゴリを表す表現で置き換える。
4. 検証用クエリで再評価し、成績が改善しない場合は別の書き方（枠組みの変更）を試す。
5. 1024 文字以内を確認し、更新する。

## 3. 出力評価

対象スキルに `evals/` が無い場合は、作成または改修の依頼であれば本節の手順で `evals/evals.json` と `evals/trigger-queries.json` を新規に作成してここで作成を完了する。**監査のみの依頼では作成せず、評価の不実施と理由を報告する。**

### 3.1 評価方式の選択（必ず 1 つを選び、記録する）

| 方式 | 適用条件 | 手段 |
|---|---|---|
| **A. 機械的 assertion** | 出力が客観的に検証できる（ファイルの変換・抽出・生成・定型手順・値の検証） | `evals/evals.json` の `assertions` に、検証可能な文として記述する |
| **B. 人手レビュー** | 出力が主観的（文体、意匠、設計品質、表現の妥当性） | 出力と期待値を並べて利用者に見せ、フィードバックを得る |
| **C. A + B** | 客観部分と主観部分が混在する | 両方を実施する |

- **選択の判断そのものを記録する**（例: 「本スキルは出力に客観的な検証可能な項目が含まれるため A と C を採用」）。記録しないと次回以降に判断の再現性が失われる。
- assertion は**機械で判定できる項目だけ**に使う。主観的な品質を assertion 化しない。

### 3.2 テストケースの書き方

- まず 2〜3 ケースから始める。最初の一周の結果を見る前に投資を膨らませない。
- プロンプトは現実の利用者が書きうるものにする。文面の揺らぎを混ぜる（くだけた文面、精密な文面）。境界条件（不正な入力、曖昧な要求、解釈が分かれる指示）を少なくとも 1 件含める。
- 期待出力は人が読める形で書く。

### 3.3 スキーマ

`evals/evals.json` に保存する。

```json
{
  "skill_name": "target-skill-name",
  "evaluation_mode": "assertion | human | both",
  "mode_reason": "評価方式を選んだ理由",
  "evals": [
    {
      "id": 1,
      "prompt": "利用者が実際に書きうる要求",
      "expected_output": "期待される結果の説明",
      "files": [],
      "assertions": []
    }
  ]
}
```

- `assertions` は最初の周では空でもよい。最初の一周の出力を見てから追加する。
- assertion は**観測可能で数えられる文**にする。「出力の品質が高い」のような判定不能な文は使わない。

### 3.4 実行と比較

- 各ケースを **with_skill と baseline の 2 回**実行する。baseline は、新規作成なら「スキルなし」、改修なら「改修前のスナップショット」、監査のみなら「スキルなし」（改修前という概念が存在しない）とする。
- 実行ごとに**クリーンなコンテキスト**から開始する。サブエージェントを別セッションで起動すると分離できる。サブエージェントが使えない場合はセッションを分ける。どちらも使えない場合は 1 ケースずつ順に実行し、実行順を記録する。
- 出力は `with_skill` 側と baseline 側を対で保存する。

### 3.5 採点

- assertion の PASS/FAIL を、**証拠付きで**記録する。根拠は意見ではなく、出力の引用か事実（ファイルが存在する、行数が一致する等）。
- 機械で判定できる assertion はスクリプトで採点する。LLM の判断より速く、再利用できる。
- **常に PASS になる assertion と、両方式構成で常に FAIL になる assertion は修正対象ではない。** 前者は情報価値が無く、後者は assertion が不適切である。

### 3.6 終了条件

以下をすべて満たすまで反復する。

- 学習用の assertion がすべて PASS になる、または改善が見られなくなる。
- 利用者のフィードバックが空、または具体的な不満が解消している。
- トリガー評価の検証用スコアが改善している。

**終了条件を満たした後の再評価を禁止する。** 「念のためもう一度最終確認」という無停止の反復は、改善ではなく工数の浪費である。終了の判断基準は評価に書き、残件は台帳で管理する。

## 4. 評価結果の反映

- 評価で判明した失敗は、**その根本原因に対応する指示を書き換える**。個別ケースへのパッチを当てない（同じ根本原因の別ケースが再発する）。
- 実行トレース（最終出力だけでなく）を読む。エージェントが無駄なステップを踏んでいるなら、その指示の書き方が原因である。
- 評価の過程で見つかった反復作業（各ケースでエージェントが同じヘルパースクリプトを書いていた等）は、`scripts/` に束ね化する。
