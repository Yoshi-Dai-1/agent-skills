# 実行時規律（Runtime Protocol）

対象スキルが**実行時に**遵守すべき規律。対象スキルの `SKILL.md` にこの内容を組み込むための指針をここに示す。対象ドメインに依存しない共通部分のみを記述する。

## 1. 計画の構造化と検証（Plan-Validate-Execute）

- 一括実行や破壊的な操作の前には、**構造化された中間計画**を作成する。計画には対象の一覧、実施手順、完了条件を含める。
- 計画は**正本と照合して検証する**。照合はスクリプトで行うか、機械可読の基準に対して行う。照合が失敗したら計画を修正して再検証し、通過してから実行する。
- 検証できない計画は、検証可能な計画に書き直す。書き直してもなお検証できない場合は、実行せず、検証の手段と理由を報告して利用者の判断を仰ぐ。**検証不能な計画をそのまま実行しない。**

## 2. 対象全件の列挙と完了条件

- 実行計画には、**対象を全件列挙した一覧**と、**完了条件（対象件数と、実行・精読・スキップの内訳）**を明記する。
- 完了条件に「全部」「全体」のような限度を意味しない語を用いない。**件数を明記する。** 「全体」を宣言しながら一部のみを実施した報告は、実施範囲の過剰表示であり、再発させてはならない。
- 対象の一部に手を加えない判断をした場合は、その対象と理由を計画に記す。実行中に判断を変える場合は、実行前に変更後の計画について合意を得る。

## 3. 範囲変更の事前合意

- 合意済みの対象範囲を、**合意なく縮小も拡大もしない。** 縮める判断をした場合は、実行前に理由を示して合意を得る。
- 合意は相互の前提が一致していることを指す。前提が食い違う場合は、実行前に確認する。

## 4. 完了報告の区分

- 完了報告は、**次の 4 区分で提示する**。
  - 変更点: 当該実行で変更した内容
  - 解消: 当該実行によって解消した不備
  - 確認: 良好と確認した項目（従前から良好で変更を伴わないものを含む）
  - 残存ギャップ: 解決していない不備
- 区分できない場合は「なし」と明記する。**「解消済み」と記述しても、実際には変更していない項目を「解消」に分類してはならない。** そのような項目は「確認」に分類する。
- 検証できなかった項目は「対象外（理由）」として別枠で示す。**未実施を合格として表示しない。**

## 5. 手段の抽象化とフォールバック

- 特定のツール名や手順に固定せず、**目的指向の能力記述**とする（例: 「描画結果を取得して判定できる手段が実行環境にある場合」）。
- 手段が存在しない場合の扱いを必ず定義する。**省略する場合は、省略の事実を完了報告に含めることを義務付ける。** 省略を報告しないまま次へ進むことは禁止する。
- 手段の選択は実行時の環境に委ねるが、**判定基準は記述する。** どの手段ならどの項目を検証できるかを明示する。
- 実行者が人手である指示（目視・手動確認・実機確認）を、AI エージェントが行う手順の前提として置かない。必要な場合は「利用者へ確認を依頼する」という別枠の指示として分離する。

## 6. 同一対象には同一語

- 対象スキル全体で、同じ対象を指す語を統一する。対象スキルが成果物を生成する語と、指示文が使う語が混在する場合は、それぞれの領域で一意に決める。
- 分岐条件の語と報告の語を一致させる（同じ状態を条件節と結論で別の語で呼ばない）。

## 7. 適用範囲外の実行

- 対象スキルの範囲外の操作（業務ロジック、データ、ネットワーク送信など）を、指示なく行わない。
- 範囲外の操作が必要な場合は、実行前に理由を提示し、合意を得る。
