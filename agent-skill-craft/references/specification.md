# Agent Skills 公式仕様適合ルール

出典: https://agentskills.io/specification.md および同サイトの各ガイド。規定要件（must / Required）と推奨（should / Keep / Avoid / Recommended）を区別して記述する。

## 1. ディレクトリ構成

```
skill-name/
├── SKILL.md          # 必須: メタデータ + 指示
├── scripts/          # 任意: 実行可能コード
├── references/       # 任意: 追加ドキュメント
├── assets/           # 任意: テンプレート・静的リソース
└── ...               # 任意: 上記以外のファイル・ディレクトリ
```

- `SKILL.md` を含むディレクトリが 1 つのスキルである。追加のファイル・ディレクトリは自由である。
- したがって `references/` のサブディレクトリ、`evals/` 等の独自ディレクトリは**規格に違反しない**。配置と分割粒度は設計判断である。

## 2. YAML フロントマター

`SKILL.md` は YAML フロントマター（`---` で区切る）＋ Markdown 本文で構成しなければならない。

| フィールド | 必須 | 制約 |
|---|---|---|
| `name` | 必須 | 1 〜 64 文字。`a-z` `0-9` `-` のみ。`--` 禁止。先頭・末尾のハイフン禁止。**親ディレクトリ名と一致しなければならない** |
| `description` | 必須 | 1 〜 1024 文字。空でない。**何をするか**と**いつ使うか**の両方を含む |
| `license` | 任意 | ライセンス名、または同梱ライセンスファイルへの参照 |
| `compatibility` | 任意 | 500 文字以下。実行環境要件（対象製品・必要パッケージ・ネットワーク等）。特定の要件がある場合にのみ記述する |
| `metadata` | 任意 | 文字列→文字列のマップ。キーは衝突回避のため固有な名を推奨 |
| `allowed-tools` | 任意 | 事前許可するツールのスペース区切り。実験的 |

- 値の YAML 解析に失敗する形式（例: `description: Use this skill when: ...` のコロン）を避ける。長い description はクォートまたはブロックスカラーで記述する。
- 名称規則を満たさない場合も、クライアント実装によっては警告のみで読み込みを続行する。規格違反として扱うのは必須要件に限定する。

## 3. 段階的開示（Progressive Disclosure）

| 段 | 読み込まれるもの | 契機 | 目安サイズ |
|---|---|---|---|
| 1 | `name` と `description` | セッション開始時に全スキル分 | 1 スキルあたり 50 〜 100 token |
| 2 | `SKILL.md` 本文 | スキルが発動したとき | **5000 token 未満を推奨、500 行未満を推奨** |
| 3 | `scripts/` `references/` `assets/` 等 | 本文が参照したとき | 用途に応じて |

- 本文が長くなる場合は詳細を `references/` 等へ移す。**どのファイルをいつ読むかを本文に明記する**（「when to load」条件）。
- `references/` 配下の個別ファイルは小さいほどコンテキストを節約できる。1 ファイル 300 行を超える場合は目次を付ける（運用ルール。公式は「参照ファイルは課題ごとに絞る」ことのみを定める）。

## 4. ファイル参照

- 参照は**スキルルートからの相対パス**で記述する。
- **ファイル参照は SKILL.md から 1 段深さに収める。** 深く入れ子になった参照連鎖は避ける。`references/foo.md` は可、`references/sub/foo.md` は避ける。
- 本文での記法として実例が示されているのは 2 種である。識別できないパスを書かない。

```markdown
[the reference guide](references/REFERENCE.md) の詳細を参照する。

scripts/extract.py を実行する。
```

- **スクリプト実行パスはスキルディレクトリルート基準の相対パスである。** エージェントはそのディレクトリを起点に実行する。`node <スキルディレクトリ>/scripts/verify.js` のような可変パスの埋め込み要求は使わない。

## 5. スクリプト（scripts/）

公式仕様が明示しているのは「自己完結していること、または依存を明示すること」「適切なエラーメッセージを含めること」「境界条件を適切に扱うこと」の 3 項目である。以下の残りは公式の運用ガイド（using scripts）由来の運用ルールであり、公式の必須要件ではない。

- 自己完結していること、または依存を明示すること。
- エラーメッセージは**何が悪く、何を期待し、どうすればよいか**を示すこと（運用ルール）。
- `--help` で使い方・選択肢・使用例・終了コードを公開すること（エージェントが最初に読む接点である）。
- 終了コードを意味のある値に分ける。
- 出力は構造化形式（JSON / CSV / TSV）を推奨する。**データは stdout、診断・進捗・警告は stderr** に分離する。
- 対話的な入力（TTY プロンプト・パスワード・確認メニュー）を要求しないこと。エージェントは非対話シェルで実行するため、入力を待つスクリプトは停止する。入力はフラグ・環境変数・stdin で受け付ける。
- 冪等であること。`create if not exists` 型の安全な既定動作とする。
- 入力制約は曖昧な入力を推測で埋めずに明示的に拒否すること。
- 破壊的・状態変更を伴う操作には `--dry-run` を用意する。
- 出力量の上限を考える。ハーネスが一定量で切り詰めるため、既定は要約とし、必要なら `--offset` 等の分割取得手段を用意する。

## 6. 検証

- 公式の検証ライブラリで検証する（公式仕様が挙げる手段）。

```bash
skills-ref validate ./my-skill
```

- このライブラリは `SKILL.md` のフロントマター有効性と命名規約を検証する。静的検証のみで本文の品質は保証されないため、本スキンの Phase 3 は機械検証と証拠付き自己監査を併用する。

## 7. description の書き方（発動度の決定要因）

- **命令形（命令文）で書く。**「このスキルは〜を行う」ではなく「〜 whenever … use this skill when …」とする。エージェントは「発動すべきか」を判断するので、行為の指示として記述する。
- 実装ではなく**利用者の意図**に焦点を置く。エージェントは利用者の要求文と照合して発動を判断する。
- **pushy に書く。** エージェントは自力で扱えるタスクではスキルを参照しない傾向があり、undertrigger が起きやすい。利用者が領域名を明示しない場合も含めて発動条件を強く列挙する。
- 簡潔に保つ。数文から短い段落まで。1024 文字の上限に注意。
- `optimizing-descriptions.md` の手順で発動率を測定する。`should_trigger` 10 件・`should_not_trigger` 10 件程度のクエリ集合を評価し、各クエリ 3 回の実行で発動率を算出する。過学習を避けるため学習用 60% と検証用 40% に分割する。
