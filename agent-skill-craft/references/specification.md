# Agent Skills 公式仕様適合ルール

出典: https://agentskills.io/specification.md および同サイトの各ガイド。
**数値と規則の正本は `assets/agent-skills-spec.json`** である。**下の表の数値は正本との一致を機械で検証する。** 下の表にない項目は `assets/agent-skills-spec.json` を参照すること。

## 1. ディレクトリ構成

`SKILL.md` を含むディレクトリが 1 つのスキルである。

| ディレクトリ | 必須 | 内容 |
|---|---|---|
| `SKILL.md` | 必須 | メタデータと指示 |
| `scripts/` | 任意 | 実行可能コード |
| `references/` | 任意 | 必要に応じて読み込むドキュメント |
| `assets/` | 任意 | テンプレートと静的リソース |

上記以外のファイルとディレクトリも置ける。配置と分割粒度は設計判断である。

## 2. フロントマター

YAML フロントマター（`---` で区切る）＋ Markdown 本文で構成する。

| フィールド | 必須 | 制約 |
|---|---|---|
| `name` | 必須 | 1 〜 64 文字。`a-z` `0-9` と単独のハイフンのみ。先頭・末尾のハイフンと連続ハイフンは禁止。**親ディレクトリ名と一致しなければならない** |
| `description` | 必須 | 1 〜 1024 文字。何をするかといつ使うかを含める |
| `license` | 任意 | ライセンス名、または同梱ライセンスファイルへの参照 |
| `compatibility` | 任意 | 500 文字以下。実行環境要件。特定の要件がある場合にのみ記述する |
| `metadata` | 任意 | 文字列から文字列へのマップ。キーはほかのスキルと重ならない名前を推奨 |
| `allowed-tools` | 任意 | 事前許可するツールのスペース区切り。実験的であり、サポートはクライアントによって異なる |

- 値の YAML 解析に失敗する形式（例: `description: Use this skill when: ...` のコロン）を避ける。長い description はクォートまたはブロックスカラーで記述する。
- 名称規則を満たさない場合も、クライアント実装によっては警告のみで読み込みを続行する。**規格違反として扱うのは必須要件に限定する。**
- `name` の検証は `ASCII`（`a-z`・`0-9`・ハイフン）に限定する。公式は `unicode` 小文字英数字に言及するが、例示は `ASCII` のみであるため、厳格側の限定とする。

## 3. 段階的開示（Progressive Disclosure）

| 段 | 読み込まれるもの | 契機 | 目安 |
|---|---|---|---|
| 1 | `name` と `description` | 全スキル分をセッション開始時に読み込む | 1 スキルあたり 100 token 程度 |
| 2 | `SKILL.md` 本文 | スキルが発動したとき | 5000 token 未満、500 行未満を推奨 |
| 3 | `scripts/` `references/` `assets/` | 本文が参照したとき | 用途に応じて |

- 本文が長くなる場合は詳細を `references/` へ移す。**どのファイルをいつ読み込むかを本文に明記する。** 書き方は `references/authoring.md` の 10 節に従う。
- `references/` 配下の個別ファイルは小さいほどよい。1 ファイル 300 行を超える場合は目次を付ける（運用ルール）。

## 4. ファイル参照

- 参照は**スキルルートからの相対パス**で、**1 段深さ**に収める。深く入れ子になった参照連鎖は避ける。
- **スクリプト実行パスはスキルディレクトリルート基準の相対パスである。** `node <スキルディレクトリ>/scripts/verify.js` のような可変パスの埋め込み要求は使わない。

```markdown
[the reference guide](references/REFERENCE.md) の詳細を参照する。

scripts/extract.py を実行する。
```

## 5. スクリプト（scripts/）

公式仕様が明示しているのは自己完結すること、依存の明示、分かりやすいエラーメッセージ、境界条件の適切な扱いの 4 項目である。以下は公式の運用ガイド由来の運用ルールであり、公式の必須要件ではない。

- `--help` で使い方・選択肢・使用例・終了コードを公開する（AI エージェントが最初に読む接点である）。
- 終了コードを意味のある値に分ける。
- データは stdout、診断・進捗・警告は stderr へ分離する。
- 対話的な入力を要求しない。AI エージェントは非対話シェルで実行するため、入力を待つスクリプトは停止する。入力はフラグ・環境変数・stdin で受け付ける。
- 冪等であること。`create if not exists` 型の安全な既定動作とする。
- 破壊的・状態変更を伴う操作には `--dry-run` を用意する。

## 6. 検証

```bash
skills-ref validate ./my-skill
```

このライブラリはフロントマターの有効性と命名規約を検証する。機械走査だけでは本文の品質は保証されないため、Phase 3 は機械走査と証拠付き自己監査を併用する。

## 7. description の書き方（発動度の決定要因）

- **命令形で記述する。**「このスキルは〜を行う」ではなく「〜 whenever … use this skill when …」とする。AI エージェントは発動すべきかを判断する。したがって行為の指示として記述する。
- 実装ではなく**利用者の意図**に焦点を置く。AI エージェントは利用者の要求文と照合して発動を判断する。
- **pushy に書く。** AI エージェントは自力で扱えるタスクではスキルを参照しない傾向があり、undertrigger が起きやすい。利用者が領域名を明示しない場合も含めて発動条件を強く列挙する。
- 簡潔に保つ。目安は 100 token 程度である。
- 発動率の測定手順は `references/evaluation.md` の 2 節に従う。

## 8. 適合の3者区別

適合の問いは 3 者で区別する。混同しないこと。

- **本スキルの適合**: 本スキル自体が公式仕様に適合したスキルであること。構造・書き方ともに適合する。
- **対象スキルの適合**: 本スキルで作成・検証する対象スキルが公式仕様に適合していること。必須要件は機械で完全検証し、推奨事項は警告と自己監査で担保する。
- **検証スクリプトのカバレッジ**: 検証スクリプトが公式条文を判定できる範囲。必須要件は正本駆動で完全検証し、推奨・曖昧領域は警告と `skills-ref` への委譲で扱い、差異は注記として残差管理する。

書き方の公式適合に関する軽微な差異は次の 2 点であり、いずれも対応方針を定めて管理する。

- 見比べテストは新旧どちらの出力か伏せて利用者に見せる（`references/evaluation.md` の 3.1 節）。
- 実行記録にはかかった時間の目安を 1 行添える（`references/evaluation.md` の 3.4 節）。
