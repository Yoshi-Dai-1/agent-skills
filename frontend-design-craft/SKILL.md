# Frontend Design Craft Skill

ユーザーインターフェース（UI）の構築・監査・改修において、W3C ARIA APGのアクセシブル構造と指定デザインシステムの規約を適用するための決定論的実行プロセスを定義する。

## 概要と前提
- **既存コード優先継承**: 既存プロジェクトにおいては、正本ファイルの有無にかかわらず、まず既存のコード構成（依存定義、スタイリング設定、既存コンポーネント等）をスキャン・解析し、確立されている技術スタックおよびスタイリング手法をそのまま継承・適用すること。
- **適用範囲**: 本スキルの範囲内はページ骨格・テキスト・操作性（00基盤）、見た目の適用（01）、検証（Phase 3）とする。範囲外は業務ロジック・API・DB、文案・素材の創作、プロダクト意思決定（何を作るか）であり、これらには手を加えないこと。

## 段階的実行フェーズ（Phase Protocol）

### Phase 0: 条件確定と環境・SSoT解析（Check Gate & Context Analysis Protocol）
1. **デザインSSoT（信頼できる唯一の情報源）の探索と継承**:
   - リポジトリ内からデザインSSoTファイル（例: `tokens.json`, `theme.json` 等のトークン定義ファイル）を探索し、存在する場合は正本として読み込み、トークン構造および指定スタイルを優先すること。
   - デザインSSoTファイルが存在しない場合は、既存のコード自体（CSS変数、Tailwind設定、テーマ定義ファイル等）を暫定的なSSoTとして扱い、スタイル構造をそのまま継承すること。
2. **デザインSSoTの遅延生成（Lazy Persistence）**:
   - SSoTファイルが存在しない状態で、以下のいずれかの条件を満たした場合に限り、`assets/token-ssot-template.json` の構造に従い、対象リポジトリのルート直下に `design/token-ssot.json` を新規作成すること（本スキルのディレクトリ内ではない）。
     - ユーザーから「トークン化」または「設定ファイルへの保存」の明示指示があった場合
     - 既存コードに定義されていない新しい共通スタイル変数を追加定義する場合
3. **デザインシステムの識別・決定**:
   - ユーザープロンプト内にデザインシステムの明記がある場合は、その指定に従うこと。
   - プロンプトに指定がない場合は、プロジェクト内のCSS変数や設定ファイルから使用デザインシステムを識別すること。
   - 識別できず `references/01-design-system/` 配下に複数のデザインシステムフォルダが存在する場合のみ、選択肢を提示しユーザーに確認すること。ひとつのみ存在する場合は、確認を挟まずそれを自動決定すること。ただし探索したSSoT・既存コードのデザインシステムと不一致の場合は自動決定せず、適用見送りをユーザーに報告すること。
4. **作業方針の確定**:
   - 作業モード（新規構築／監査のみ／改修）を確定すること。監査のみではコードを変更しないこと。
   - 準拠度（L1／L2／L3）を確定すること。L1は00基盤のみ、L2はL1に01の適用を加えたもの、L3はL2に違反ゼロまでの反復修正を加えたもの（監査のみの場合は描画確認を含む徹底監査）とする。なお、`00基盤`は `references/00-foundation/` の内容、`01`は決定されたデザインシステムフォルダの内容を指す。
   - ユーザー事前指示がある場合は確認を省略し即座に実行に移ること。曖昧な場合のみ1行でユーザーに確認すること。作業モード・準拠度のいずれか一方が未指定の場合は、指定済み項目を確定した上で未指定項目のみ1行でユーザーに確認すること。
5. **コンテンツ・機能の保護**:
   - 既存画面のテキスト（見出し・本文・説明文）、画像等の内容、フォーム項目と入力仕様、ボタン機能・リンク先、UXフローを100%保護すること。

### Phase 1: 事前監査と具体的修正案の提示（Pre-Audit & Proposal Protocol）
1. **違反箇所（ギャップ）の特定**:
   - コードを書き換える前に既存コードの違反箇所（W3C ARIA APG構造、WCAG 2.2アクセシビリティ、画面幅対応、指定デザインシステム規約）を特定すること。
   - デザインSSoTが存在しない場合は、プロジェクト内に未定義の独自クラス名や変数を直接出力することを禁止とし、既存コードの記法に整合させた修正案とすること。
2. **修正案の事前提示**:
   - 「どの要素の何が違反で、テキストや機能を保護したままどう修正するか」をPhase 0-4で確定した作業モード・準拠度に応じて箇条書きで事前にユーザーに提示すること。
3. **新規構築時の事前合意**:
   - 作業モードが新規構築の場合は、コード生成前に構成案（画面・コンポーネントの配置計画）を箇条書きで提示し、ユーザーの確認を得てからPhase 2へ進むこと。既存コードがある改修の場合は前項の修正案提示がこの役割を果たすため追加の構成案は不要。

### Phase 2: 連番規約ファイルの順次適用（Sequential Execution Protocol）
1. **連番ファイルのロード**:
   - 決定されたデザインシステムフォルダ（`references/01-design-system/` 配下の該当ディレクトリ）に存在する連番ファイルを番号順に検出すること。連番ファイルが1件も存在しない場合はコードを出力せずユーザーに報告すること。
   - 参照ファイル内の `§N` 記法は当該ファイルの `## N.` 見出しを指す。
2. **1ターン1ファイルの段階的適用**:
   - 作業モードが監査のみの場合はコードの出力・変更を行わず、監査結果の報告に留めること。
   - 準拠度がL1の場合は連番ファイルの読込み・適用を省略し、00基盤に沿った出力で確定させること。
   - 最初の連番ファイル（`01-*.md`）を読み込み、該当規約に対するコードを出力・確定させること。
   - 次の連番ファイル（`02-*.md`）を読み込み、追加差分コードを適用・出力・確定させること（以降、全連番ファイル終了までターンを分離して順次繰り返すこと）。
   - 複数ファイルの一括読み込み・一括出力を禁止する。

### Phase 3: 自動検証と自己修正（Verification Protocol）
1. **Layer 1（静的コード検証）**:
   - Node.js実行環境が存在する場合、`node <スキルディレクトリ>/scripts/verify-ui.js <対象ファイルのパス>` を実行し、WCAG 2.2基準（テキスト対比比率 4.5:1以上／大型テキスト・非テキスト 3:1以上）および適用中のデザインシステムのポインタターゲット要件（WCAG 2.2 AAの最低線は24×24 CSS px）の検証結果を取得すること。`<スキルディレクトリ>` と `<対象ファイルのパス>` は実際のパスに読み替えること。対象ファイルは対象リポジトリ内のマークアップファイルとすること（HTML／JSX／TSX／Vueテンプレート等）。CSS等のスタイル定義ファイルおよびSVG等の描画アセットは対象外とすること（Hexの正当な定義場所であり、誤検出を避けるため）。Node.js実行環境が存在しない場合は Layer 1 を省略し Layer 2 へ進むこと。省略した場合はその旨をLayer 3の報告に含めること。
   - 規約違反が検出された場合の対応は以下のいずれかとする。
     - 作業モードが新規構築または改修かつ準拠度がL3のときは、違反箇所に対応するコード修正案を生成し該当ファイルを上書き更新して再検証すること（違反ゼロまで反復）。
     - 上記に該当しない場合は違反一覧を報告し、反復しないこと。
2. **Layer 2（描画結果検証）**:
   - 実行環境に描画結果の取得・判定手段がある場合、「要素の重なり」「グリッドアライメントのずれ」「カラーコントラスト違反」「フォーカス表示の有無」「狭幅・広幅での描画崩れ」の有無を検証すること。存在しない場合は Layer 2 を省略し Layer 3 へ進むこと。省略した場合はその旨をLayer 3の報告に含めること。
   - 違反判定時の対応は以下のいずれかとする。
     - 作業モードが新規構築または改修かつ準拠度がL3のときはコード改修後に再取得・評価手順を実行すること（解消まで反復）。
     - 上記に該当しない場合は違反一覧を報告すること。
3. **Layer 3（完了報告）**:
   - 検証項目の確認を終えた後、変更点および解消・残存ギャップ一覧を整理して報告すること。
